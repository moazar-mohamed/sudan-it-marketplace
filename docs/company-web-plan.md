# لوحة الشركات على الويب (`company_web/`)

الحالة: **المرحلة الأولى مبنية ومجرَّبة محليًا على المحاكيات، وتعديلات القواعد الموافَق عليها مكتوبة ومختبرة محليًا. لم يُنشر شيء (لا قواعد ولا مواقع ولا APK)، ولم يُرفع شيء إلى GitHub.**

## تعديلات القواعد (في `firestore.rules`، غير منشورة)
| ما | الحقل | القاعدة |
|---|---|---|
| حالة المنتج | `status`: `published` / `draft` / `archived` (غيابها = منشور) | مقبولة في `hasValidProductExtras`؛ و`orderedProductIsAvailable` ترفض طلب منتج ليس منشورًا. |
| رمز المنتج | `sku` نص حتى 60 | نفس الدالة. |
| حد التنبيه | `lowStockThreshold` عدد صحيح 0..100000 | نفس الدالة. |
| معرض الصور | `imageUrls` قائمة حتى 5 (و`imageUrl` يبقى الأولى لتراها التطبيقات القديمة) | نفس الدالة (النوع والحجم فقط، فالقواعد لا تمر على عناصر القائمة). |
| ترتيب المواصفات | `specificationsOrder` قائمة حتى 50 | نفس الدالة. |
| سبب الإلغاء | `cancelNote` نص حتى 300 مع إلغاء الشركة | `isCompanyOrderCancellation`. |
| ردّ المبلغ | `refundedAt` مرة واحدة لطلب مدفوع أُلغي | دالة جديدة `isCompanyRefundMark`. |

الاختبارات: ملف جديد `platform_admin_web/rules-tests/company-panel.rules.test.ts` (25 اختبارًا ناجحًا). الفحص الشامل لكل ملفات القواعد القديمة يُشغَّل للتأكد أن شيئًا لم ينكسر، وأهمها اختبار حد التعبيرات في إنشاء الطلب (`order-expression-limit`).

**ما عُدّل في العميل لتحترم الحالة:** `customer_web` (يُخفي المسودة والمؤرشف، ويرتّب المواصفات بترتيب الشركة) و`lib/features/products` في تطبيق Flutter (حقل `status` في طبقة البيانات وتصفية القائمة فقط، بلا أي تغيير في الشاشات). اختبارات: `customer_web` 79 ناجحًا، وFlutter 17 ناجحًا.

**ترتيب النشر الآمن (عند موافقتك، لا قبلها):**
1. نشر الموقع الجديد للعملاء وبناء APK يحمل التصفية، **قبل** أن تضع أي شركة منتجًا في المسودة.
2. ثم نشر القواعد. نشرها وحدها لا يضر، لكن تطبيقات العملاء القديمة ستعرض المسودة (دون إمكانية طلبها، فالقاعدة ترفضه) حتى يُحدَّثوا.
3. ثم نشر لوحة الشركة.
ملاحظة: موقع العملاء يحمل أيضًا تعديلات المفضلة غير المنشورة وتحتاج قاعدتها، فلا تنشره قبل أن تقرر في المفضلة.

**لا تظهر للعميل بعد** (تحتاج تعديل شاشات العملاء، فلم أفعله): سبب الإلغاء وحالة ردّ المبلغ، ومعرض الصور (يرى العميل الصورة الأولى فقط).

## ما هي
مشروع React + Vite + TypeScript منفصل (مثل `customer_web` و`platform_admin_web`) لمدير الشركة (`role: company_admin`). يعمل على مشروع Firebase نفسه وقواعده الحالية. التصميم من لوحة التصميم المعتمدة (عربي، RTL، خط Cairo، اللون #1565C0).

## ما بُني
| الصفحة | ما تفعله |
|---|---|
| الدخول | بريد وكلمة مرور، «نسيت كلمة المرور»، ومنع كل دور غير `company_admin` فعّال. أول دخول لحساب أنشأه المشرف يفرض اختيار كلمة مرور (`mustChangePassword`). |
| اليوم | بطاقات (بانتظار الدفع، قيد التجهيز، مبيعات 7 أيام للدفع المؤكد فقط، مخزون يحتاج تعبئة)، تنبيه المهل القريبة، قائمة عمل، تعديل سريع للمخزون، رسم المبيعات. |
| الطلبات | تحديث لحظي لآخر 50، «تحميل 50 أخرى»، تبويبات بأرقام حقيقية من الخادم، مرشحات النوع، بحث، تصدير CSV، تحريك الحالة، إلغاء جماعي «نفد المخزون». |
| تفاصيل الطلب | الإيصال مع تكبير وتدوير، أثر التأكيد على المخزون، تحذير حين لا يغطي المخزون الطلبات المعلقة (الأقدم أولًا)، تأكيد الدفع، رفض الإيصال برسالة تصل العميل في المحادثة، إلغاء الطلب المدفوع، تعيين فني، المحادثة، السجل. |
| المنتجات | جدول بتعديل السعر والمخزون داخل الصف، مرشحات، تعديل جماعي للسعر والتوفر، تصدير CSV، حذف محميّ. |
| تعديل/إضافة منتج | يحفظ **الحقول المتغيرة فقط**، المخزون لا يتأثر بالحفظ، التحقق من المواصفات المكررة، رفع الصورة من الجهاز أو بالرابط، معاينة «كما يراه العميل». |
| العروض | جارية ومنتهية على المنتجات والخدمات، إنشاء وتعديل وإنهاء. |
| الخدمات | خدماتي، إضافة من كتالوج المنصة، خدمة خاصة، وطلبات الخدمة بمراحلها مع إشعار العميل. |
| ملف الشركة | الملف والشعار والموقع، حسابات الدفع (حتى 5)، نقاط الاستلام (حتى 5)، مدن الخدمة. |
| الفريق والتقييمات | إنشاء حساب فني (تطبيق Firebase ثانٍ + دفعة واحدة)، تعديل وتعطيل، الرد على التقييمات. |

## ما صُحِّح عمّا في التطبيق (من التحليل)
1. **الحفظ لا يمسح المخزون:** يُرسل الحقل المتغير فقط، وتعديل الكمية معاملة تحسب على الرقم المخزَّن وقت الحفظ.
2. **انتهاء مهلة الـ24 ساعة** يعمل عند فتح اللوحة وكل 5 دقائق وهي مفتوحة (لا يزال بلا خادم).
3. **إشعار الإلغاء:** لا يوجد نوع إشعار لإلغاء الشركة في القواعد، فتُكتب الرسالة في محادثة الطلب ليراها العميل.
4. **فشل الإشعار لا يُظهر خطأ:** الفعل يثبت ويُقال إن الإشعار تعذّر.
5. **حذف المنتج** يُمنع مع وجود طلبات مفتوحة، ويُعرض «إيقاف البيع» بديلًا.
6. **أرقام اليوم:** المبيعات للدفع المؤكد وغير الملغى، و«بانتظار الدفع» منفصل عن «قيد التجهيز».
7. **القوائم بصفحات** (50 في المرة) بدل تحميل الكل.

## كيف تشغّله
```bash
cd company_web
npm install
npm run dev          # http://localhost:5195  (يتصل بالمشروع الحقيقي)
npm test             # اختبارات المنطق
npm run build
```
للتجربة على المحاكيات: أنشئ `company_web/.env.local` فيه `VITE_EMULATOR=1`، وشغّل `firebase-emulators` ثم `company-web` من `.claude/launch.json`.

## ما جُرِّب فعلًا (محاكيات + القواعد الحالية)
الدخول وفرض كلمة المرور، تأكيد الدفع (المخزون 4←3 وإشعار العميل)، تحريك الحالة، إلغاء طلب مدفوع (المخزون يرجع 3←4)، رفض بسبب «نفد المخزون» والمنتج يغطي الطلب (يُرفض)، إلغاء تلقائي لطلب تجاوز 24 ساعة، تعديل مخزون مع تغيّره خلف الشاشة (2←7 لا 3←8)، حفظ سعر مع تغيّر المخزون خلف النموذج، إنشاء منتج، حذف محميّ ثم حذف، عرض على منتج، إنشاء حساب فني، عرض الصفحات على 375px بلا تمرير أفقي. اختبارات المنطق: 12 ناجحة، وبناء الإنتاج ناجح.

**لم يُفحص بصريًا بلقطات** (نافذة المعاينة كانت مخفية)، فراجع الشكل بعينك.

## ما زال ينتظر قرارك
- تاريخ بداية للعرض (عروض مجدولة): أجّلته عمدًا، فتغيير حساب السعر في قاعدة إنشاء الطلب (قريبة من حد التعبيرات) وفي كل العملاء خطر، والأسلم دالة مجدولة على الخطة المدفوعة.
- نوع إشعار «ألغت الشركة طلبك»: يحتاج نصًا في تطبيق Flutter وفي relay الإشعارات (نشر relay يحتاج مفتاح Cloudflare جديدًا). اليوم تصل الرسالة في محادثة الطلب.
- رسوم توصيل لكل شركة، وسعر بالدولار.
- مهمة مجدولة لانتهاء المهلة وحجز المخزون عند الطلب (Cloud Functions، تحتاج الخطة المدفوعة).

## لم يُبنَ بعد
استيراد CSV، صفحة المحادثات والإشعارات (شارة الرسائل في الشريط العلوي)، منتقي الخريطة (الإحداثيات تُكتب أرقامًا)، الإنجليزية، الوضع الداكن.

## للنشر لاحقًا (بموافقتك)
1. موقع Hosting جديد (اسمه قرارك) وملف `firebase.company.json` مثل `firebase.customer.json`.
2. رفع الصور من الجهاز يحتاج الخطة المدفوعة وإنشاء حاوية التخزين ثم نشر `storage.rules`.
3. الاستعلامات المستعملة تعتمد على الفهرس الموجود `(companyId, createdAt)` وعلى دمج الفهارس المفردة، فلا أتوقع فهارس جديدة (المحاكي لا يفرض الفهارس، فتُتحقق عند أول معاينة).
