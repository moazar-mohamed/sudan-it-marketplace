# Sudan IT Marketplace – Platform Admin Web

Separate React + TypeScript + Vite dashboard for the `platform_admin` role. It uses the
same Firebase project (Auth + Firestore, client SDK only) as the Flutter app and does not
change the Flutter app or any Firebase account.

```bash
npm install
npm run dev         # http://localhost:5173
npm run typecheck   # tsc --noEmit
npm run lint
npm test            # access-control unit tests
npm run test:rules  # Firestore rules tests (local emulator, needs Java; see below)
npm run build
```

Sign in with an existing Platform Admin account. After sign-in the app reads
`users/{uid}`; only `role == "platform_admin"` with `isActive == true` gets in, anyone
else is signed straight back out. This is a UX gate; the Firestore rules are the real
enforcement (`../firestore.rules`).

## What Platform Admin can do

| Area | Permission |
| --- | --- |
| Companies | View all. **Add** a company together with its company-admin login (created active, unrated): the form takes the company email and an **initial password** (at least 6 characters, Firebase Authentication's minimum). The login is created in Firebase Authentication with a second, throw-away Firebase app instance (no Admin SDK, no Cloud Functions), and the company and the admin's `users/{uid}` profile (`role: company_admin`, `companyId` = the new company's exact document id, `mustChangePassword: true`) are written in one batch, so the two ids can never differ. The password is never stored in Firestore. On first sign-in the company must choose its own password before the company workspace opens; the company can sign in immediately with the email and initial password. A location can be given as a written address, as an exact point picked on a map (Leaflet + OpenStreetMap tiles, no API key), or both; coordinates are optional and saved as numbers (`latitude` / `longitude`). Change **status only** (`pending`, `active`, `rejected`, `inactive`): approve / reject a pending company, activate / deactivate. Each row opens the company's details when clicked anywhere outside its buttons; the row's actions are **Delete | Deactivate** (there is no separate View button). **Delete** asks for confirmation that lists what is deleted and states that orders are kept, then (for an active company) deactivates it first, because only a non-active company can be deleted. Deleting cascades: the company, its company-admin profile, its employees (technician records and profiles), technician invites, products, company services, reviews and the admin's/employees' notifications are deleted in batches (safe to re-run). **Orders are never deleted** (the rules forbid it for everyone), and customers, customers' notifications and other companies are untouched. Firebase Authentication sign-in accounts cannot be removed from the browser and must be deleted separately in the Firebase console. Profile fields of an existing company are not editable. Only active companies and their products are visible to customers. |
| Customers | View all customers (filters: All / Active / Inactive). **Add** a real customer account (created with a second, throw-away Firebase app instance; the customer sets their own password through an emailed link). **Edit** name and phone only. **Deactivate / reactivate** (`isActive` only; a deactivated customer cannot use the customer app, and their data and orders are kept). **Delete is not available**: a real deletion must also remove the Firebase Authentication account, which needs the Admin SDK or a Cloud Function. Role, `companyId`, uid, email and other protected fields cannot be changed. |
| Products | Browse, with a Hidden filter. **Hide** a product from customers with a written reason (the company sees it, on the product and in its list) or **show** it again, and **end a running offer**. Nothing else on a product changes: price, stock and the rest stay the company's (the rules reject any other key). A hidden product is left out of the customer app, cannot be ordered (rule), and is still listed for its company. Orders already placed are untouched. |
| Orders | The list reads **50 orders at a time from the server** (newest first) with "Load 50 more". **It updates by itself**: the first page is a live listener (a new order or a status change appears without a refresh button, and only the changed orders are read), the status counts are read again when it changes, and the older pages you loaded stay in place. Filters on the server by status, company and a **date range** (From / To); the chips show the server's count of each status. The search box filters the rows already loaded; to find any order use the search (Ctrl+K). The lists the dashboard flags (`?attention=`) come from the dashboard's own read. Status, payment and assigned technician are visible and managed by the company. **Cancel order** is the one thing Platform Admin does: only while the order is Processing (payment waiting or confirmed), with a required reason kept in the activity log, and the cancel reason `admin` ("Cancelled by the platform"). The stock an order took (payment confirmed, or an older order) goes back to its own company's product, exactly the order's quantity and once, in the same batch; the rules check every part (`isPlatformAdminOrderCancellation`, `isStockReturn`). A confirmed payment is refunded by the company outside the app. |
| Categories | One tree drawn as a **card per main category** (a coloured tile with its icon or first letter, the Arabic and English names, how many sub-categories and products/services it holds, an active / inactive tag); what is open under it sits inside the card with guide lines. Each row has "add sub-category" (shown on hover for sub-categories) and a "⋯" menu (edit, move, order up / down, activate / deactivate, delete). Inactive categories are dimmed. **Active / Inactive** chips (with counts) narrow the tree by each category's OWN flag, keeping the path above every match (so an inactive parent of an active child is shown as the way to it); ordering is switched off while narrowed, like while searching. |
| Reviews | Read-only. |
| Analytics | Read-only. A period (7 / 30 / 90 days, 12 months, all time) drives the figures: orders, sales value (cancelled orders are no sale), confirmed payments, average order, completed, cancelled and cancel rate, why orders were cancelled, and the top 10 companies and products by sales. Below, fixed 12-month series of orders, sales and new customers. **Export orders (CSV)** downloads the selected period's orders in the browser (UTF-8 with BOM for Excel; text that starts with `=`, `+`, `-` or `@` is neutralised so a spreadsheet cannot run it as a formula). Everything is computed in the browser from the live collections. |
| Offers | Every offer running now on a product or on a company's service, with the one action Platform Admin has on it: **end it** (price, end time and badge are cleared together; the normal price and everything else stay). On a company's service link Platform Admin can do nothing else (`isPlatformAdminServiceOfferEnd`): not the price, the note or the on/off switch, and it cannot create a link; only the company does. |
| Exports | Every list can be saved as CSV (UTF-8 with a BOM so Excel reads Arabic). **Orders**: the button on the Orders page exports every order the current filters match (status, company, dates), read in pages of 500 up to 5,000 (the toast says when the cap cut it short; narrow the dates for the rest). **Products**: the rows on screen. **Analytics**: an **Export (CSV)** menu with the orders of the selected period and three sales files: **by day** (Khartoum days: orders, confirmed orders and sales, awaiting, cancelled), **by company** and **by product** (every one with a confirmed sale, best first). Companies, Customers and Reviews export their visible rows. |
| Use of the app | A closed card at the bottom of Analytics that reads only when opened: people who opened the app each day (last 14 days), new customers each day, and the products opened most. The apps write one tiny `usage_days/{day}_{uid}` document per person per day (once, never changed) and add one to `product_stats/{productId}` when a customer opens a product (once a day per product per phone); the panel only COUNTS them on the server, so it costs a few dozen reads. Only Platform Admin reads them; nothing personal is stored. Counting starts when the app began reporting use; earlier days read 0. A person on a hacked client could inflate the figures (there is no server to check). |
| Reports | What customers, company admins and technicians send from the app (**Settings > Report a problem**): a reason (order problem, payment, a company's conduct, product issue, app problem, other), a subject, what happened and, optionally, an order number. Stored in `reports/{id}`: the sender writes it once in their own name (new, no reply, server time) and reads only their own; Platform Admin reads all and changes only the **status** (new / in progress / closed) and a written **reply** the sender reads in the app under **My reports** (the rules allow nothing else, and nobody deletes a report). The page lists them with a status filter, search, sortable columns and a dialog with the full text, the sender, the order and a link to the company; the sidebar badge counts the new ones. Handling a report is written to the activity log. **At most 5 reports per person in any 24 hours**, enforced by the rules the same way as the order limit (a `report_quota/{uid}` document with five time slots written in the same batch as each report; the app also checks first and says so). **Notifications**: moving a report to *In progress* or *Closed* writes a notification in the same batch (type `report_in_progress` / `report_closed`, the report's own subject as its only text, to the customer or to the company, one per report and type; the rules check the report really is in that status) that the app shows in its notification list and opens My reports from; the panel then asks the push relay for the phone push (best effort; needs the relay to be deployed with the report texts: `push_relay/` already has them, the deployed worker does not until it is redeployed). New reports reach the admin through the sidebar badge, the bell (a row linking to the list), the number in the browser tab title and a toast when one arrives while the panel is open. Technicians' reports get no notification (they have no notification list for it). |
| Admins | The people who can sign in to the panel (System group). Any active admin **adds** another (name + email): a second, throw-away Firebase app creates the Authentication account with a random password nobody sees, the signed-in admin writes `users/{uid}` (`role: platform_admin`, `isActive: true`, exactly those fields, `createdAt` = server time), and a password-setup email goes to the new admin. If the profile cannot be saved the new account is deleted again. An admin can **switch another admin off or on** (only `isActive` changes) but never themselves, and nobody can be deleted or turned into an admin from here. Admins have equal power, so add only people you trust. |
| Profile | Your account: name, role, email, when you joined and last signed in (Firebase Auth metadata), a link to Admins, sign out. **Security** (a card that opens downward, closed at first): change your own password (the current one is checked again first; minimum 6 characters) or email yourself a reset link. Language and appearance live only in Settings. |
| Settings | Every card is **closed until its title is pressed** (the arrow turns and the body opens downward; what was typed stays when it is closed) and says what it holds on its closed face: the language, the appearance, and whether each notice is on, scheduled or off. |
| Settings > Notices in the apps | Three notices stored in `platform_settings/public` (readable by everyone, even before sign-in; written only by Platform Admin), each saved with an activity entry and shown with a **preview** of how it looks on the phone, in Arabic and English. **Maintenance**: the mobile apps show it instead of the app while it is on (Platform Admins are never locked out). **Announcement**: a banner for everyone, customers or companies, of a **kind** (information, warning or good news, each with its own colour and icon) that a user can dismiss (remembered per text, kind and link). Both have an Arabic and an English text of at most 300 characters (some text while on), an optional **schedule** (start and end; the notice appears and disappears by itself, and a maintenance with an end shows "Expected back ... in about 2 h 15 min"), and an optional **button** that opens an https page (a status or support page on maintenance; a label of at most 40 characters in each language). A status line says whether a notice is off, scheduled, showing or already over. **Required update**: the lowest app build allowed (the number after `+` in the version) and the https page to update from; an older app is stopped on an "Update required" screen with an Update button. It only works on apps that already contain this feature (build 6 and later): earlier apps cannot see it, and they also ignore schedules, buttons and kinds (they show a notice as soon as it is switched on, until it is switched off). An app whose build cannot be read is never stopped, and Platform Admins are never stopped. Times use the schedule's clock on the phone, so a phone with a wrong clock shows a scheduled notice at the wrong time. Not built: a configurable order limit (the 10-per-24-hours limit is a fixed 10-slot ring in the rules and the shipped app) and push broadcasts (they need the push relay redeployed). |
| Scale | **Orders are no longer opened whole.** The Orders list reads a page of 50 and a count per status; an order's page reads that one document; a customer's page reads that customer's orders; a company's page reads a count; the Customers list is paged 25 at a time and counts the orders of the customers on screen only; Analytics reads the last 12 months (366 days), and every order only when "All time" is chosen. These queries need composite indexes (`../firestore.indexes.json`), which take a few minutes to build after they are deployed: until then the list says it could not be loaded. Products, Reviews, Service Requests, Customers and Companies are still read whole (live), which is fine for thousands of documents but is the next limit to move to pages. The dashboard uses counts and small queries. |
| Search and alerts | **Search** (Ctrl+K or `/`, or the box in the top bar) opens a window with every page and, as you type, companies, customers (by name or e-mail), orders (by customer name or the start of the order number) and products. It uses small "starts with" queries (a few documents each, after a 300 ms pause), so it finds what a name starts with, not the middle of a word; Latin names are tried as typed, in lower case and capitalised because stored names are case-sensitive. **Alerts**: a bell in the top bar shows how many records need attention (the dashboard's own rules) with the list, plus what is only waiting for others (service requests, payments to confirm); a fresh read that finds more than the one before shows a toast, and the browser tab's title carries the number, e.g. "(3) ...". The figures refresh every five minutes while the tab is visible. |
| Lists | The Companies page can be narrowed to active companies with no products after 3 days (`?attention=noProducts`); Companies, Customers and Reviews export their visible rows to CSV. The sidebar shows a badge on Orders, Service Requests, Reviews and Companies with the number of records that need attention (the dashboard's own counts). Orders, Companies, Customers, Products, Reviews and Offers have **click-to-sort headings** (ascending, descending, back to the page's own order; empty values always last; a screen reader hears `aria-sort`), denser rows and a header that stays in view while the table scrolls. While a list loads it shows grey placeholder rows (and a shimmering bar for a figure still being read) instead of a spinner. |
| Appearance and menu | **Dark mode** follows the device, like the mobile app (the same palette; the brand blue and the Cairo font do not change); Settings > Appearance can force light or dark and is remembered in this browser (`platform_admin_theme`). The menu is grouped (Operations, Catalogue, Community, System) and can be collapsed to icons on a computer screen (remembered). On a phone the hamburger button is replaced by a **bottom bar** (Dashboard, Orders, Service Requests, Companies, and **More** for the rest), with the same attention badges. |
| Dashboard | Greets the signed-in admin by first name and says when the figures were read. There is no "needs attention" panel on the page any more: the same rules (payments unverified for over 24 hours in red; paid orders not completed after 5 days, service requests unanswered for over 48 hours and 1-2 star reviews of the last 14 days in yellow; active companies with no product after 3 days in grey) live in the **alerts bell** in the top bar and in the sidebar badges, each count linking to the list narrowed by the same rule (`?attention=...`). **Trend cards** for orders, confirmed sales (cancelled and unconfirmed excluded), new customers and the cancel rate, each against the period before it, with a small line of the last days under the figure; a green change is good news and a red one is bad (a falling cancel rate is green), and an arrow carries the direction as well so colour is never the only signal. A **period selector** (7 / 14 / 30 days) next to Refresh drives the cards and the **daily confirmed-sales line chart**; the chart's days (24-hour slots ending when the figures were read) add up to exactly the card's figure. The thresholds are constants in `src/data/stats.ts`. |
| Activity log | Read-only trail of what Platform Admin changed from this dashboard (company status / add / delete / registration, customer add / edit / access, review hide / show, category and service changes): who, what, which record, when. Stored in `admin_audit_log`, append-only: the rules let an active Platform Admin add an entry in their own name with the server's time, and nobody edit or delete one. A change that is one write carries its entry in the same batch; a change that spans many writes records its entry after it succeeds (a failure to record never undoes it). The page shows the newest 300 entries. |

The privilege requires `role == "platform_admin"` **and** `isActive == true`; a
deactivated admin loses all of it.

Language: English (LTR) and Arabic (RTL), switchable from the top bar.

## Rules tests

`npm run test:rules` starts the Firestore emulator (first run downloads it) and runs
`rules-tests/platform-admin.rules.test.ts` against `../firestore.rules`. It uses fake
identities inside the emulator only; nothing touches the real project. On Windows the
emulator's Java process can outlive the command; if the next run says port 8080 is
taken, stop that leftover `java` process.

## Deploying

The rules in this repository are not live until they are deployed to the Firebase
project (`firebase deploy --only firestore:rules`). Until then the dashboard runs
against the previous rules, under which Customers and Reviews cannot load.
